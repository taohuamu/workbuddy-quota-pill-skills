# 运行逻辑

最后对照代码：2026-11-14（技能 0.4.2）

一句话：技能不是程序，是一份给模型看的说明书加一组只读脚本，由宿主在会话里按需唤起。
没有进程、没有窗口、没有服务、没有注册表项。

---

## 一、安装与加载

安装 = 把目录放进 `~/.workbuddy/skills/`，卸载 = 删掉。没有注册步骤。

宿主要在**会话启动时**扫一遍这个目录，把每个技能的 `name` 和 `description` 读进内存。
所以「装完当前会话没反应」不是缺陷，是加载时机：技能清单已经定型了，新装的要等下个会话。
包里给的 `install.py --copy` / 默认的目录联接，区别只在源目录能不能删——
联接指着工作区，改了即时生效；复制是快照，改了要重装。

---

## 二、五段链路

**1. 路由** —— 你发一句话，模型拿着所有技能的 `description` 自己判断要不要调。
整条链路里只有这一步是不确定的，其余四步都是确定性代码。这也是为什么
`tools/route_test.md` 必须真发问句：静态检查只能证明「问句里有能对上的词」，
证明不了模型会选它。

**2. 注入** —— 命中后宿主把 `SKILL.md` 全文塞进上下文，并把 `${CODEBUDDY_SKILL_DIR}`
替换成技能目录的绝对路径。所以 SKILL.md 里可以直接写变量，不必写死路径。
异机的会话归档里能看到实证：模型收到的正文里，变量已经是
`C:/Users/<用户名>/.workbuddy/skills/quota-pill`。

**3. 执行** —— 模型按「快速指导」跑 `quota_report.py`。必须绝对路径：工作目录在项目里，
不在技能目录，相对路径必然 `can't open file`。

**4. 数据层** —— `build_report()` 全量扫 `projects/*/*.jsonl`，逐行取
`providerData.rawUsage.quota`，按 `reset_at` 判断是否还在本周期，再用近 15 分钟数**涨了几个百分点**。

**5. 出表** —— 6 列 Markdown，末行固定带取数耗时与日志目录。模型只被允许原样贴、
补一句结论，不许重排行序、四舍五入改写数字、删末行。

## 三、周期归属、预测与等级

**周期归属。** `reset_at` 是字符串形式的 Unix 秒。它代表「下一次重置的时刻」，
本周期起点 = 它往前推 24 小时。`now > reset_at + 60s` 就判定为停在上一周期
（60 秒是抖动宽限），这些模型被过滤出表，只在末行报「另有 N 个停在上一周期」。
判据只看 `reset_at`，跟快照多久以前无关——一条两小时前的快照只要还没到重置时刻，
仍然算本周期，只是「数据新鲜度」会显示两小时前。

**预测**（0.5.0 起由 `forecast.py` 做，报告和通知共用同一份实现）：

- **观测：数百分点。** 取近 15 分钟内的每一次正向跳变，累加幅度（回退记 0，一次跳多个
  百分点按实际幅度计）。为什么不用端点差分：15 分钟里可能有 40 条快照，端点差分只用其中 2 条，
  整数百分比下涨 1 个百分点就是 4 个百分点/小时、量化误差 100%；碰上服务端的 ±1 回退还会被算成负贡献。
  涨幅是泊松过程在窗口内的充分统计量，量化误差只有 1/k。
- **读数：换成时间。** `λ|k ~ Gamma(k+½, W)`、`T|λ ~ Gamma(R, λ)`，于是
  `T/(T+W) ~ Beta(R, k+½)`，取 Beta 分位反解 T。主数用 50% 分位。k=0 时不给时间——
  中位可以到 40 小时也可以到 7 小时，而「窗口内没涨」是观测事实、「零消耗」才是猜测，只报前者。
- **判定：唯一的布尔量。** 提前提醒要求 χ² 单侧下界 `λ_L ≥ (100−p)/2 小时`，
  单次误报率 0.20；同时要求已用 ≥55%（剩余太多时两小时外推没有意义），
  并且已用 <80%（到了 80% 交给百分比条件，避免同一状态两条通知）。

**等级 = 用量带 + 一条速度判定。** ≥95% → 触限；≥80% → 注意；其余 → 正常；
另外，若窗口内涨够 4 个百分点（`tier=ok`）且中位时间早于距重置时间，也升为「注意」——
否则会出现「已用 38%、两小时后到上限、状态正常」这种自相矛盾的卡。样本少时不升级，
只在该行标「样本少」。0.4.x 那条「低置信度且 ≥80% → 按最坏打算」仍然不回来。

进程退出码只有两种含义：`1` 表示有模型处于触限等级（`--json` 里的 `has_risk`），
`0` 表示没有。**「注意」不算风险**，所以退出码 1 不是错误。

`verdict` 是数据层给表格用的完整句（"重置前就会耗尽"这种），0.5.0 起由 `forecast.attach()`
用同一句话覆盖成结果句，报告与通知都从这里取：

- 窗口内有新增 → 「按此速度约 40 分钟后到上限」
- 窗口内没有新增 → 「近 15 分钟无新增」
- 中位时间晚于重置 → 「本周期内到不了上限」
- 距重置不足一个窗口 → 「即将重置」（这时快照是全的，不能写「数据不足」）
- 一条快照都没有 → 「数据不足」

**只换说法，不碰数据层**——数据层只加了一个可选参数 `loaded=`（让报告和预测共用一次
全量扫），`sync_check` 同时校验 `quota_watch.py` 与 `forecast.py` 两个哈希。

## 四、缓存

按「日志文件集合 + 纳秒 mtime + 大小」签名，TTL 300 秒，缓存文件在
`%LOCALAPPDATA%\quota-pill\skill-cache.json`。

它在活跃会话里几乎必然失效：签名覆盖的 jsonl 里包含当前会话自己那份，你每跑一次命令，
这份日志就长一截，签名必变。这是对的——数据真的变了，就该重算。

要验证缓存层本身没坏，把两次调用放进同一条命令跑，期间日志不动，第二次就会显示命中：

```bash
python scripts/quota_report.py && python scripts/quota_report.py
```

## 五、唯一写盘的地方

脚本对会话日志只读。所有写入都在 `%LOCALAPPDATA%\quota-pill\` 下：

| 文件 | 谁写 | 作用 |
|---|---|---|
| `skill-cache.json` | `quota_report.py` | 签名缓存，删掉只是下次重扫 |
| `notify-state.json` | `notify.py` | 同一模型同一等级的 2 小时冷却 |
| `runtime\` | `install_task.py` | 提醒脚本的运行副本：`notify.py`、`quota_watch.py`、`phrasing.py` 三个文件 |
| `install.json` | `install_task.py` | 安装时的间隔与阈值，供 `--status` 回读；卸载时删除 |
| `notify.log` | `notify.py` | 每次检查留一行，超 200 KB 轮转成 `.1` |

`install.json` 记的是「安装那一刻」，不是「任务当前值」——脚本不去解析任务定义（两条
后端的 `Arguments` 格式不同），所以有人手改过任务时两者会不一致。要核对实际阈值，
看 `notify.log` 每行末尾，或直接读任务动作。

删掉整个目录不会损坏任何功能。

## 六、和托盘版的边界

| | 托盘版 | 技能版 |
|---|---|---|
| 形态 | 常驻小窗，开机自启 | 只在提问时被唤起 |
| 谁渲染 | 自己用 Tk 画三态 | 宿主渲染 Markdown |
| 输入框避让 | GDI 像素带探测 | 没有，也不需要 |
| 数据层 | 同一份 `quota_watch.py` | 同一份，逐字节 |
| 提醒 | 内置 | 可选附件，靠计划任务 |
| 单次成本 | 常驻内存 + 定时刷新 | 0.04 秒命中缓存 / 1.7 秒重扫 |

数据层共用同一份实现，所以两边算出来的数必然一致——这是「报告和托盘窗口对得上」的原因，
也是 `sync_check.py` 用哈希守着的理由。

提醒是唯一会改变系统状态的部分，它把「什么时候叫」和「叫了说什么」分成两件事：

- **触发**看两个条件：任一模型已用 ≥80%，或 `forecast` 判定「按当前速度 2 小时内会到上限」
  （且已用已过 55%）。
- **内容**取并集：触发者 ∪ 所有 `level=critical` 的模型。正文只给结果，不报依据。

分开是有原因的。`critical` 里有一批「才用 26%、但按当前速度撑不到重置」的模型，它们会
长期存在；拿它们当触发条件，通知就变成每两小时一次的常驻噪音。可一旦因为别的原因叫醒了，
这些恰恰是该看的——所以放进内容，不放进触发。反过来，85% 但没在动的也在内容里，否则
「80% 就提醒」这个承诺落不了地。

正文长这样，**不带涨幅与速率**：

```
deepseek-v4.1-flash 已用 81%，按此速度约 67 分钟后到上限
deepseek-v4.1-flash 已用 93%，近 15 分钟无新增
```

0.4.x 的「X 小时内触限」不再出现：那是把条件式推断说成了 wall-clock 承诺，而实测里
报警后用户停手，承诺就不成立。

它与报告底部那行「注意」因此**互不包含**：85% 平缓的会通知、不进注意行（注意行只认
`level=critical`，即 ≥95%）；26% 撑不到重置的进注意行、却不单独通知。
阈值都能改（`--pct` / `--warn` / `--floor`），但它们不是运行时读配置，而是**写进任务动作的参数**——
所以改完必须重跑一次安装。`--status` 会打出安装时的阈值（读 `install.json`），
任务实际用过的值看 `notify.log` 每行末尾那几个数。

## 七、已知失效模式

每一条都在真机或异机上出过，不是假想：

1. **相对路径调用** → `can't open file 'scripts/quota_report.py'`。必须用绝对路径。
2. **把 `reset_at` 当数字算** → 整列重置时间变空。它是字符串。
3. **拿单次差分的速率反推结论** → 说出「按这个速度并非撑不到，而是早就触发了上限」这种
   自相矛盾的话。整数百分比下，15 分钟内涨 1 个百分点就是 4 个百分点/小时，端点差分等于在噪声上做除法。
   0.5.0 起改成按百分点计数，这条不复存在；但引用旧版本的数字时要记得它换过口径。
4. **把「表里只有一个模型」说成「只统计了当前会话」** → 扫描范围是全部历史会话。
5. **`schtasks.exe` 被客户端的程序黑名单拦** → 进程根本起不来（1 毫秒内 `WinError 5`）。
   两台互不相关的机器表现一致，说明这是宿主沙箱自带的策略，不是某台机器的安全设置。
   降级到 PowerShell 的 ScheduledTasks 模块可以正常注册，所以降级链是必需品。
6. **「第二次还是重新扫描」被误判为缓存坏了** → 见第四节，这是正确行为。

## 八、没有做的事

- **增量读日志**：每次全量扫。日志大了会慢，靠缓存兜，而缓存经常失效。
- **历史库**：不落库、不累积，每次都从原始日志重算。跨周期对比只能靠翻日志。
- **跨平台验证**：查询层没写死 Windows API（就是 glob + json），理论上能跑；
  提醒层用了 WinRT toast 和任务计划程序，是 Windows 专有。没测过的一律不声称支持。
- **`allowed-tools` 粒度**：`Bash(python:*)` 是否真的只放行了 python，没验过。
- **多技能竞争的触发**：同时装积分、用量类技能时「额度」这个词归谁，没测过。
