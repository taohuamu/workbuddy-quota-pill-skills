## 1. 扫描结果与 Bug 台账

### 扫描方式

不是看代码猜，是把它的判据推到极端场景跑一遍：把一份 references 的 mtime 改到未来
（等价于「明天重新 clone 一次」），内容一个字不动。

```
$ touch -t 202611250900 quota-pill/references/data-source.md
$ python quota-pill/scripts/sync_check.py
references 时效提醒（不阻断）：
  - data-source.md：内容改于 2026-11-25，头部仍写 2026-11-20
```

### 台账

**编号**：B22
**发现轮次**：R16
**所属维度**：资源层（脚本判据）/ 输出层（给出的结论是错的）
**复现步骤**：`touch -t 202611250900 quota-pill/references/data-source.md`（内容不变）→
`python quota-pill/scripts/sync_check.py`
**实际结果**：报「内容改于 2026-11-25，头部仍写 2026-11-20」，并建议「改了内容就把日期一并改掉」。
**预期结果**：内容没变，不该报；这条提醒的语义是「内容改过但日期没跟」。
**严重级别**：P2（不阻断，但结论与事实相反）
**根因**：`check_reference_dates()` 用 `os.path.getmtime()` 当内容日期。clone、解压、
复制都会把 mtime 刷成当下 —— 换台机器、或任何人重新拉一次仓库，三份 references
会全部被误报。误报的代价是这条检查被当成噪音、进而被忽略（真改内容时也就不看了）。
**状态**：已修

## 2. 本轮改动计划

### 编号：C35

**类型**：修 Bug
**关联**：B22；验证用例 T31
**基线问题**：见上。
**改动**：
1. 新增 `content_date(path) -> (date, 来源)`：
   - `git status --porcelain -- <file>` 为空且有 `git log -1 --format=%cs` → 用**最后一次提交日期**；
   - 有未提交改动、或不在 git 仓库里 → 退回 mtime；
   - 返回来源说明（「最后一次提交」/「未提交改动，按 mtime」/「无 git 记录，按 mtime」）。
2. `check_reference_dates(ref_dir)` 收目录参数（原用模块常量），便于测试指向临时目录。
3. 提醒文案带上依据：`内容改于 X（未提交改动，按 mtime），头部仍写 Y`。
**依据**：B22 的复现记录；原则是「判据要能区分『内容变了』与『文件被复制了』」，
mtime 做不到，git 的提交日期可以。
**验证**：见第 3 节。
**结果**：保留。
