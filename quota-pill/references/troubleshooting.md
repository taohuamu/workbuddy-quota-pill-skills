# 排查顺序

上次核对：2026-11-14

按顺序查，命中即停。每一步都给出「看到什么算这一步有问题」。

## 1. 一个模型都没有

- 先看末行的日志目录是否存在、里面有没有 `projects/*/*.jsonl`。
- 目录为空 → 还没产生带 `quota` 的记录，正常对话一轮再看。
- 目录不存在 → WorkBuddy 可能装在别处，检查环境变量 `WORKBUDDY_HOME`。

## 2. 某个模型不在表里

- 可能原因一：本周期没用过它。
- 可能原因二：服务端没给它的响应下发 `quota`（`glm-5.3-flash` 长期如此）。
- 判断方法：换成该模型聊一句，再跑 `--no-cache`。仍不出现即为原因二。
- 结论写法：「该模型本周期没有可用配额数据」，不要补 0%。

## 3. 数字长时间不动

- 看「数据新鲜度」：几小时前属正常，很多模型字段稀疏。
- 若新鲜度是「几秒前」而百分比没变，说明服务端本轮下发的就是同一个值。
- 不要解释成「本地缓存没刷新」——缓存是 300 秒内按文件签名复用，日志一变就重扫。

## 4. 重置时间显示为「—」

- 该模型最后一条记录没有 `reset_at`。
- 若整列都是「—」，检查是否把字符串当数字做了减法（`reset_at` 是字符串）。

## 5. 「另有 N 个停在上一周期」

- 这是正常的过滤：这些模型的 `reset_at` 已过 60 秒以上，属于上一周期的残值。
- 不要把它们的百分比算进「本周期用量」。

## 6. 查询很慢

- 首次调用要全量扫描，日志大的机器上可能 1–3 秒。
- 日志静止时第二次命中缓存约 0.1 秒；活跃会话里边跑边写日志，每次都会重扫（见下一条）。
- 想确认是扫描慢还是缓存失效：加 `--no-cache` 对比末行的耗时。

## 7. 连着跑两次，第二次还是「重新扫描」

签名是「文件集合 + 纳秒 mtime + 大小」，覆盖被扫描的全部 jsonl，其中**包含当前会话自己的日志**。
你每跑一次命令，这条日志就被追加一次，签名必然变化，TTL 没到期也照样失效。

这不是缺陷：数据确实变了，就该重算。要证明缓存层本身没坏，把两次调用放进同一条命令跑——
期间日志不动，第二次就会显示「命中缓存」：

```bash
python scripts/quota_report.py && python scripts/quota_report.py
```

真实能命中的场景是「日志不再增长时」：新开会话、先别提问，直接查。
